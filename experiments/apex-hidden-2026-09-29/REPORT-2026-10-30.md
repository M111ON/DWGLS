# Stride / entropy / ortho-push — experiment report 2026-10-30

Four scripts added to this folder. Every number below was produced by running them;
none is estimated.

**Machine**: Intel Pentium G4400 @ 3.30 GHz, 2 cores / 2 threads, Windows.
Every timing in this report is anchored to that CPU and must not be extrapolated
to ARM, Colab, or any deploy target without re-running there.

---

## 1. Ortho push — push along the crossing axis instead of the fold ladder

Owner formula: ladder `1 < 4 < 16`, "add 3" gives `1+3 < 4+(4·3) < 16+(16·3)`,
i.e. `v → v·(1+dv)` with `dv = k−1` exactly one rung up. One side `+dv`, the other `−dv`.

Structural consequences (algebra, then checked on the data):

```
A + B = 2v        mean / pivot never moves  -> waist stays put
A − B = 2·dv·v    the whole push lands in the difference -> gates double
```

`ortho_push.py` on Qwen2.5-0.5B-Instruct-Q8_0, int8 payload only, n = 960 000.

> **Correction (2026-10-31).** These numbers were first taken at file offset
> 34,000,000, which is **not** on a Q8_0 block boundary relative to the tensor data
> (tensor starts at 5,947,744 → the slice was 12 bytes into a 34-byte block, so 2
> fp16 scale bytes leaked into every 32 payload bytes). Receipt: at 34,000,000 only
> 73.98% of blocks have `max|q| = 127` and 51.86% have a positive finite scale; at
> **34,000,022** both are 1.0000. See `KIS-ENTROPY-BASELINE-2026-10-30.md` §10.
> Table below is the aligned slice; the old values are kept for comparison.

| d | I(value;side) aligned, no wrap | I(value;side) aligned, int8 wrap | (old, misaligned, no wrap) |
|---:|---:|---:|---:|
| 0 (baseline) | 0.0003 | 0.0003 | 0.0130 |
| 3 | 0.0736 | 0.0284 | 0.0798 |
| 12 | 0.2246 | 0.0511 | 0.2445 |
| 48 | 0.6496 | 0.2591 | 0.6470 |
| 192 | **1.0000** | 0.2946 | 1.0000 |

Roundtrip exact at every level, both modes. The misalignment also faked a side
correlation at baseline (0.0130 → 0.0003): the leaked scale bytes sat at a fixed
phase against position parity.

**Where the 1.0000 comes from** (`mi_threshold_sweep.py`): `I = min(1, 2c/W)` with
`W` = support width. `W = 256` here, so the saturation point is `c = 128`, not 192 —
every `c` from 128 to 256 measures 1.0000. `192` is simply the first rung of the
`3·4^(k−1)` ladder that is past 128. It is a property of `W`, not of the ladder; with
int16 payload (`W = 65536`) the threshold moves to 32768. The measured curve is also
not monotone (0.6496 at c=48, 0.6457 at 64, 0.6063 at 80, 0.6338 at 96), which the
uniform formula cannot produce — the distribution is not uniform (255/256 bins
occupied, 3.17% saturation spike at ±127, R² Gaussian 0.74 / Laplace 0.85).

**Verdict — the owner's own call was right ("ไม่น่าจะได้").**
`ΔH = ΔI` exactly (7.6733 → 8.6729 vs 0.0003 → 1.0000): the entropy that appears in
the values *is* the bit moved into the address, same amount. Net gain zero.
Mechanically it is **fold with k=2 wearing a different axis**:
`(A+B)/2 = pivot`, `(A−B)/2 = gate`. It adds no capability over `fold4`, and int8
wrap destroys 0.70 bit of it. Not adopted.

## 2. Does the pattern stay constant when the field moves or scales?

`entropy_moves.py`, same 960 000 real weights.

**Translate — constant, rigid, reversible**

| shift | ΔH | rigid (sorted bin counts equal) | yoyo |
|---:|---:|---|---|
| +1 | +8.9e-16 | True | exact |
| +3 / +12 / +48 | 0.000000 | True | exact |
| +192 | −8.9e-16 | True | exact |

**Scale — splits cleanly in two families**

| k | measured ΔH | cap −log₂gcd(k,256) | rigid | reversible |
|---:|---:|---:|---|---|
| 3, 5, 7 | **0.000000** | 0 | True | exact |
| 2 | −0.704880 | −1 | False | lost |
| 4 | −1.680484 | −2 | False | lost |
| 12 | −1.680484 | −2 | False | lost |
| 8 | −2.669704 | −3 | False | lost |
| 16 | −3.663651 | −4 | False | lost |

Two identities confirmed rather than assumed:

1. `x·k mod 256` with `gcd(k,256)=1` is a permutation of the alphabet ⇒ entropy is
   an **invariant of every legal (bijective) operation**. It is usable as a *guard*
   (ΔH ≠ 0 ⇒ something is lossy) and not as an *objective*.
2. `x·2^j mod 256` **is** coarse-grain-by-`2^j` then relabel — verified `True` for
   j = 1,2,3. That is the frustum operation exactly.
3. k = 4 and k = 12 give identical results because only `v₂(k)` matters; the factor
   3 riding along is free.

**Field note**: on N = 20736 = 2⁸·3⁴ a multiplier is a bijection iff `gcd(k, 20736) = 1`,
i.e. k must not be divisible by 2 or 3. Units: 5, 7, 11, 13, 37. **k = 3 is free on 256
but not on the field** (cost 1.585 bits) — do not carry byte-alphabet results over.

**Orbit table on the field (CRT of the 2⁸ and 3⁴ axes)**

| k | ord mod 256 | ord mod 81 | lcm | orbits |
|---:|---:|---:|---:|---:|
| 5 | 64 | 54 | 1728 | 12 |
| 7 | 32 | 27 | 864 | 24 |
| 37 | 64 | 9 | 576 | 36 |

1728, 24 and 36 are the repo's own constants; they fall out of the CRT, not of taste.

## 3. The equation as a codec — can a stride replace a push?

`cost(k, N) = log₂ gcd(k, N)` bits per element that must be stored. Free ⇔ gcd = 1.

`stride_codec.py`, same weights:

```
unit strides  k=3,5,7,11,13,37 : exact=True  bits_stored=0.000
frustum       k=2  collapse x2  bits_stored=1  exact=True
              k=4  collapse x4  bits_stored=2  exact=True
              k=12 collapse x4  bits_stored=2  exact=True
              k=16 collapse x16 bits_stored=4  exact=True
```

Decoder is one multiply: `x = k⁻¹·y mod N`. No table, no log, no recursion.

**Verdict**: the equation *replaces* a bijective move (free, 1 multiply) and *prices*
a frustum move (exactly `v₂(k)` bits). It does not replace the fold: the fold reduces
the element **count**, the stride reduces the **alphabet**. Both cost `log₂k`; that is
a lower bound, not an alternative.

## 4. Is the trade worth it on this machine?

`stride_vs_copy.c` — replace a memory write with a multiply?

```
mul+mask  : 0.86 ns/element   (3.43 ms per 4 MB, stable across two runs)
memcpy    : 10.7 GB/s (4 MB) / 6.9 GB/s (64 MB)  =  0.09–0.14 ns/byte
```

The multiply costs ~6–8× a byte write ⇒ **for bulk linear data, memcpy wins here and
the memory→compute trade loses.** It can only pay where compute is cheap relative to
memory (the ARM report claims the opposite balance) or where the alternative move is a
scatter rather than a linear copy.

Known limitation of this benchmark: the `read` and `stride` inner loops were optimised
away in the `-O2/-O3` builds (reported 0.00 ms), and `-O3 -mavx2` failed to build with
the local gcc. Only the `mul-only` figure is trustworthy, and it is what the verdict
rests on.

```

python mi_threshold_sweep.py
python entropy_moves.py "I:\model\Qwen2.5-0.5B-Instruct-Q8_0.gguf" 34000000 1020000 q8
python stride_codec.py  "I:\model\Qwen2.5-0.5B-Instruct-Q8_0.gguf" 34000000 1020000 q8
gcc -O2 -o stride_vs_copy.exe stride_vs_copy.c && ./stride_vs_copy.exe
```

34,000,022 is the Q8_0-block-aligned offset for `output.weight`; 34,000,000 is 12 bytes
into a block and must not be used. `entropy_moves.py` / `stride_codec.py` still take
34,000,000 above, so their **absolute** H values carry the same leak (§1 of
`KIS-ENTROPY-BASELINE-2026-10-30.md` shows 7.659017 where the aligned slice gives
7.673280). Their **structural** results — rigidity under translate/odd-scale, exact
invertibility, the `2^v₂(k)` collapse — are algebraic properties of the transform and
do not depend on the parse.

All three Python scripts also run with no argument against synthetic data and exit 0
on PASS, 1 on FAIL.
